The SPG has never been through a firmware loader, and it cannot be run by the BaseConf firmware at all; on top of that it breaks a rule of the SPG format that every loader relies on. Two separate problems, both fixable.

What I found

1. Our emulator side-loads the SPG. evo-run and evo-play read the file themselves (tools/evo-emu/evo.c), fill the RAM pages and jump to $8000. The firmware's own loader has never seen build/dune.spg. So make verify proves nothing about starting on a real machine.

2. The BaseConf firmware (EVO Reset Service) does not run SPG files. Its file browser's type table in the ROM lists DIR, TRD, SCL, FDI, TAP and "Unknown", nothing else; the only place "SPG" appears is a nine-name extension list whose dispatcher handles TRD/SCL/FDI/TAP and treats everything else as a disk image to mount as a RAM disk. I checked two ROMs: the one the emulator ships (ERS v0.55b) and the current one in tslabs' zx-evo repository (ERS v0.57e, TS-BIOS dated 2024). SPG is a TS-Conf format: TS-BIOS runs it under the TS-Conf configuration, and on BaseConf it was run through Wild Commander. The forum confirms it: "SPG files do not start from the built-in browser on BaseConf". The current Wild Commander and its "Improved" fork are TS-Conf programs (they page through the #xxAF ports); only the 2012-2013 versions targeted BaseConf.

3. The file itself is illegal for any loader. The SPG v1.0 spec (pentevo/docs/Formats/SPGv1_0.txt) says a block's page must be #00-#DF, because the loaders keep themselves in #E0-#FF. Our tools/spg.py writes the Tutorial's data into pages 249-254 (#F9-#FE). Observed on the firmware in the emulator: after boot the ERS holds data in pages F4, F5, F7, FA, FD, FE (16 KB of resident code) and FF. Wild Commander's SPG runner copies itself to page FE and runs from there. So whichever loader opened our file would overwrite itself while loading page FA, FD or FE and die before reaching the game. That matches "can not start at all" if a Wild Commander was used; with the ERS browser alone nothing at all happens.

What we can do

A. Move the Tutorial out of #F9-#FE (must do in any case). Free pages under #E0 by src/pages.inc: 220-223 (the unused end of the sound reserve), and 0, 4, 6 (the screens are 1/3/5/7). Seven pages, the Tutorial uses six. Change TUT_PAGES in tools/dune_tutorial.py, PG_TUT_DATA in pages.inc, and the sound-set check that says the sound pages must end below the Tutorial's. Also make write_spg refuse any page above #DF so it cannot come back.

B. Give the game a BaseConf-native way in: a TRD with our own loader. The ERS mounts a .trd from the SD card as drive A and boots it, that is the normal way to start anything on BaseConf. The boot program would read DUNE.SPG straight from the card's FAT: talk to the SD card over the SPI ports #57/#77 (BaseConf manual section 9.7, the card is already initialised by the firmware), walk the FAT16/FAT32 root directory and cluster chain, and place the blocks where the block table says, then map the windows and jump to $8000 - the same logic as evo_load_spg in C, in Z80, plus SD and FAT reading (about 2-3 KB). Wild Commander's DSDZC.ASM (SD driver) and CORE32.ASM (FAT core) are open source and document the protocol. TR-DOS's virtual drives are no alternative: 4 x 640 KB is less than the 3.2 MB and slow.

C. Alternatively, run it through an old Wild Commander on BaseConf after fix A. I could not confirm which versions still work on BaseConf, so this is the fallback, not the plan.

Not an option: TS-Conf. The user's combined firmware can boot TS-Conf, and TS-BIOS runs SPGs, but the game is written for BaseConf hardware (ATM EGA screen, the xxF7 manager, the shadow ports), so it would need a port of the port.

Two things I need from you: how exactly was it started on the real machine (the ERS browser, Wild Commander, something else) and what was on screen, and the ERS version line ("EVO Reset Service vX.XX" at the top of the reset menu) - the 09.03.2023 string is the FPGA configuration, not the ERS.

Also done during the research, uncommitted: evo-run and evo-play take --sd F.img (a raw card image: MBR plus one FAT partition), and a script command sd F.img, so the real firmware can read a card in the emulator. That is how the firmware was observed. Its file browser draws in a text mode libxpeccy does not render (black screen), so I read page 5 by hand instead; noted in .claude/docs/emulator.md. A card image builder (mksd.py) is in the scratch directory, not in the repo.
